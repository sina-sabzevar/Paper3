# مشخصات لیبل — نسخهٔ ۱ (قفل‌شده)

> این سند قرارداد لیبل است. هر تغییری در آن یعنی مدل باید از نو آموزش ببیند،
> پس تغییرات را نسخه‌بندی کنید (`v1`, `v2`, …) و نسخه را در خروجی ذخیره کنید.

## ۰. واقعیت‌های سیستم که این طراحی بر آنها سوار است

| واقعیت | منبع | اثر روی لیبل |
|---|---|---|
| تاریخ پرداخت هر قبض موجود است | billing | DPD ماهانه مستقیماً محاسبه می‌شود |
| **قطع میان‌دوره = رسیدن مصرف به سقف اعتبار** | network/billing | **از تعریف «بد» خارج** — فیچر است نه لیبل |
| **قطع دوطرفه ≈ ۳ ماه عدم پرداخت** | billing | رویداد نکول قطعی — داخل تعریف «بد» |
| ۱۸ تا ۲۴ ماه تاریخچه | — | ۲ تا ۴ کوهورت مشاهده |

---

## ۱. خط زمان

```
   ◄──── پنجرهٔ فیچر: ۹ ماه ────►  │ T0 │  ◄──── پنجرهٔ لیبل: ۶ ماه ────►
                                    │    │
            فیچرها فقط از اینجا    │    │     لیبل فقط از اینجا
```

- **پنجرهٔ فیچر = ۹ ماه.** با ۱۸ ماه تاریخچه جا می‌شود. اگر ۲۴ ماه داشتی، ۱۲ ماه بگذار.
- **پنجرهٔ لیبل = ۶ ماه تقویمی، ولی ۴ قبض.**

این تمایز مهم است و معمولاً اشتباه گرفته می‌شود:

```
 T0        T0+1      T0+2      T0+3   │   T0+4     T0+5     T0+6
 ├─قبض۱────┼─قبض۲────┼─قبض۳────┼─قبض۴─┤                        │
 │                                     │                        │
 │◄──── ۴ قبضی که اقساط رویشان می‌نشیند ──►│◄─ ۲ ماه فرصت تا قبض۴ به ۶۰ روز برسد ─►│
 │◄──────────────── پنجرهٔ مشاهده: ۶ ماه ─────────────────────►│
```

- **۴ قبض** شمرده می‌شود (نه ۶) چون وام ۴ قسطی روی همین ۴ قبض تسویه می‌شود
- ولی تا **T0+6** رصد می‌شوند، تا قبض چهارم هم فرصت داشته باشد به آستانهٔ بد برسد

اگر فقط ۴ ماه رصد کنی، نکولِ قسط آخر هرگز دیده نمی‌شود و نرخ بد سیستماتیک کم برآورد می‌شود.
شرط ② هم «۲ ماه از ۴ قبض» است، نه از ۶.

### کوهورت‌های مشاهده

هر کوهورت ۱۵ ماه داده لازم دارد (۹ فیچر + ۶ لیبل).

| تاریخچهٔ موجود | تعداد کوهورت | فاصله | استفاده |
|---|---|---|---|
| ۱۸ ماه | ۲ | ۳ ماه | کوهورت ۱ آموزش/تست، کوهورت ۲ خارج از زمان |
| ۲۱ ماه | ۳ | ۳ ماه | دو تا آموزش، آخری خارج از زمان |
| ۲۴ ماه | ۴ | ۳ ماه | سه تا آموزش، آخری خارج از زمان |

**کوهورت آخر هرگز وارد آموزش نمی‌شود.** فقط یک بار، در پایان، برای گزارش عملکرد واقعی.

## ۲. تعریف DPD

### دورهٔ صورتحساب (تأییدشده)

```
۱ شهریور ─── کارکرد ─── ۱ مهر ─── مهلت مجاز ─── ۱۵ مهر ─── دیرکرد ───►
                          │                        │
              bill_outstanding_amt            سررسید
                  پر می‌شود                بعد از این، تأخیر
```

- کارکرد ماه M در ابتدای ماه M+1 وارد `bill_outstanding_amt` می‌شود
- تا **۱۵ ماه M+1** مهلت مجاز است و دیرکرد حساب نمی‌شود
- به محض پرداخت، `bill_outstanding_amt` صفر می‌شود

### فرمول

```
DPD = طول بازهٔ پیوستهٔ (bill_outstanding_amt > 0)  −  ۱۵
```

| رفتار | طول بازه | DPD |
|---|---|---|
| روز دهم پرداخت کرد | ۱۰ روز | **۰** |
| روز دهمِ ماه بعد پرداخت کرد | ~۴۰ روز | **۲۵** |
| اصلاً پرداخت نکرد | بازه‌ها به هم می‌چسبند | رشد می‌کند |

مبنا **سررسید (۱۵ام)** است نه تاریخ صدور. اگر مبنا را صدور بگذاری، نیمی از جامعه هر ماه
«دیر» می‌شوند و نرخ بد بی‌معنا بالا می‌رود.

هیچ تطبیق پرداخت‌به‌قبض لازم نیست و هیچ وابستگی به `v_fact_cust_bil_daily` نمی‌ماند —
یک ستون از جدول روزانه کافی است.

### `unbill_outstanding_amt` — بدهی لحظه‌ای

قبض ماه قبل **به‌علاوهٔ** کارکرد روزشمار ماه جاری. نسبتش به سقف اعتبار **دقیقاً همان
کمیتی است که قطع میان‌دوره را شلیک می‌کند**، پس فیچر «چقدر نزدیک لبه زندگی می‌کند»
از آن ساخته می‌شود:

```
ceiling_utilisation = unbill_outstanding_amt / credit_ceiling
```

### و تفکیک دو نوع قطعی را دقیق می‌کند

```
قطع + bill_outstanding_amt > 0 و روزِ ماه > ۱۵   →  عدم پرداخت  →  بد ✓
قطع بدون قبض معوقِ باز                            →  سقف اعتبار  →  فیچر ✗
```

## ۳. قاعدهٔ لیبل

در پنجرهٔ لیبل (۶ ماه):

| شرط | تعریف | پارامتر |
|---|---|---|
| **①** | `max(DPD) ≥ 60` | `BAD_DPD = 60` |
| **②** | `تعداد ماه با DPD > 15` ≥ `2` | `LATE_DAYS = 15`, `N_LATE = 2` |
| **③** | **قطع یک‌طرفهٔ بابت عدم پرداخت** رخ داد | تفکیک از قطع سقف اعتبار با تست بدهی معوق |
| **④** | تشدید به قطع دوطرفه | **شدت**، نه ماشه |

### چرا یک‌طرفه و نه دوطرفه (اصلاح نسبت به نسخهٔ اول)

قطع یک‌طرفه بعد از **۳ ماه** عدم رفع، به دوطرفه تشدید می‌شود. پس دوطرفه یک شاخص
**تأخیری** است و دو مشکل دارد:

- **سه ماه دیر شلیک می‌کند** — وام ۴ قسطه تا آن موقع تمام شده
- **سانسور راست:** قطع یک‌طرفه در ماه آخر پنجره نمی‌تواند قبل از بسته شدن پنجره
  دوطرفه شود، پس خرابی‌های اواخر پنجره سیستماتیک دیده نمی‌شوند و نرخ بد کم برآورد می‌شود

قطع یک‌طرفه رویداد **به‌موقع و قابل مشاهده** است. تشدید به دوطرفه به‌عنوان درجهٔ
شدت نگه داشته می‌شود، نه به‌عنوان ماشهٔ لیبل.

### تفکیک دو منشأ قطع یک‌طرفه

قطع یک‌طرفه دو علت دارد: عدم پرداخت، و رسیدن مصرف به سقف اعتبار. فقط اولی رویداد
اعتباری است. بدون کد دلیل، با **وضعیت بدهی همان ماه** تفکیک می‌شوند:

```
قطع یک‌طرفه + بدهی معوق از سیکل قبل‌تر  →  عدم پرداخت  →  بد ✓
قطع یک‌طرفه بدون بدهی معوق               →  سقف اعتبار  →  فیچر، نه لیبل ✗
```

### چهار نسخه، هر چهار محاسبه و گزارش می‌شوند

| نسخه | تعریف | انتظار |
|---|---|---|
| `y_severe` | ④ به تنهایی | فقط تشدیدشده‌ها — کمترین نرخ بد |
| `y_strict` | ① یا ③ | سخت‌گیرانه، نزدیک نکول بانکی |
| `y_v1` | ① یا ② یا ③ | **پیشنهاد اولیه** |
| `y_v2` | ① یا ③ یا (`N_LATE = 3`) | حد وسط |
| `y_loose` | ② به تنهایی | فقط برای دیدن اینکه چقدر شل می‌شود |

انتخاب نهایی از روی نرخ بد واقعی انجام می‌شود. **بازهٔ هدف: ۵ تا ۱۵ درصد.**

## ۴. قطع میان‌دوره — فیچر، نه لیبل

```
❌ از لیبل خارج:  رسیدن به سقف اعتبار = رفتار مصرفی، نه بدحسابی.
                  واردش کنی، پرمصرف‌ترین مشترکینت را «بد» برچسب زده‌ای.

✅ به فیچر اضافه: n_midcycle_cuts_9m           تعداد قطع میان‌دوره
                  avg_days_to_restore           میانگین روز تا رفع قطع با پرداخت
                  max_days_to_restore
```

`avg_days_to_restore` ارزشمند است: خودِ قطع بد نیست، ولی اینکه چند روز طول بکشد تا طرف
پول بدهد و خطش وصل شود، سرعت دسترسی او به نقدینگی را نشان می‌دهد.

---

## ۴.۵ قطع دوطرفهٔ گذشته — حذف یا نگه داشتن؟

**قاعدهٔ حاکم: جایگاه رویداد روی خط زمان تعیین می‌کند، نه خودِ رویداد.**

```
   ◄──── پنجرهٔ فیچر: ۹ ماه ────►  │ T0 │  ◄──── پنجرهٔ لیبل: ۶ ماه ────►
                                    │    │
        قطع اینجا = ورودی          │    │      قطع اینجا = خودِ لیبل
```

| قطع دوطرفه کِی | تصمیم | دلیل |
|---|---|---|
| **بعد از T0** | **هرگز حذف نشود** | این شرط ③ لیبل است. حذفش = پاک کردن کلاس بد |
| در لحظهٔ T0 فعال | حذف | به مشترک قطع‌شده وام داده نمی‌شود |
| ۰ تا ۶ ماه قبل از T0 | حذف (دروازهٔ سیاستی) | رویداد هنوز تازه است |
| ۶ تا ۱۲ ماه قبل از T0 | **نگه داشته و فلگ شود** | احتمال بهبود؛ تصمیم با داده |

### تلهٔ اصلی

فیلتر «قطع دوطرفه در ۱ سال گذشته» باید نسبت به **`T0`** محاسبه شود، نه نسبت به **امروز**.
اگر نسبت به امروز باشد، بخشی از پنجرهٔ لیبل را هم می‌پوشاند و دقیقاً همان مشترکینی را حذف
می‌کند که قرار بود مدل از آنها بدحسابی یاد بگیرد. نرخ بد فرو می‌ریزد و مدل بی‌معنی می‌شود.

### فیچرهای گروه بهبودیافته

```
months_since_last_twoway        تازگی آخرین قطع
n_twoway_susp_9m                تکرار
n_clean_months_since_twoway     طول دورهٔ پرداخت تمیز بعد از آن
```

### هشدار دربارهٔ Gini

حذف بدحساب‌های آشکار، مسئله را **سخت‌تر** و Gini را **کمتر** می‌کند. این شکست نیست —
بازتاب صادقانهٔ مسئلهٔ واقعی است. برگرداندن بدحساب‌های آسان برای بالا بردن Gini،
خودفریبی است: عدد بالا می‌رود، کیفیت تصمیم روی جامعهٔ واقعی تغییر نمی‌کند.

### سازگاری پنجره‌ها

طول دروازه و طول پنجرهٔ فیچر باید یکی باشد. با دروازهٔ ۱۲ ماهه و پنجرهٔ فیچر ۹ ماهه،
یک بازهٔ ۳ ماهه می‌ماند که مشترک را حذف می‌کند ولی هیچ فیچری آن را نمی‌بیند.
**یا پنجرهٔ فیچر را ۱۲ ماه کن، یا دروازه را ۹ ماه.**

## ۵. حذف از نمونه (نه بد، نه خوب — کلاً بیرون)

| مورد | چرا |
|---|---|
| اختلاف صورتحساب (billing dispute) | عدم پرداخت دلیل فنی دارد، نه ناتوانی |
| فوت مشترک | نکول نیست |
| پرونده تقلب | مدل جداگانه لازم دارد |
| خطای صدور / تعدیل صورتحساب | نویز سیستمی |
| شماره سازمانی / نمایندگی | جامعهٔ هدف نیست |
| ترک شبکه در پنجرهٔ لیبل | نتیجه ناقص است (censored) |

## ۶. ناحیهٔ نامشخص

```
indeterminate = (y == 0)  و  (دقیقاً ۱ ماه با DPD > 15)  و  (max DPD < 60)
```

نه خوب است نه بد. پرچمش ساخته می‌شود؛ حذفش از آموزش **اختیاری** است و بعد از دیدن اندازهٔ
گروه تصمیم گرفته می‌شود. اگر بیش از ۱۵٪ جامعه شد، حذفش نمونه را خیلی کوچک می‌کند.

## ۸. لیبل دوم (پیوسته) — برای تعیین مبلغ

مدل دسته‌بندی می‌گوید **به کی**. برای **چقدر** این را هم در همان استخراج بگیر، از پنجرهٔ فیچر:

```
proven_capacity = max( مبلغ قبض )  به شرط  ( DPD ≤ 0  و  pay_ratio ≥ 0.98 )
```

بالاترین صورتحسابی که ثابت کرده می‌تواند سرِ وقت بپردازد.
